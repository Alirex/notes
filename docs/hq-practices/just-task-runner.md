# just task runner

## Layout

- The root `justfile` only imports modules: one module per area in
  `just/<module>.just`.
- Every public recipe is `<prefix>-<action>`, has `[group('<group>')]`, and a
  one-line comment right above it (shown by `just --list`). Of a
  multi-line comment only the last line is shown, so use `[doc('…')]` for longer text.
  Helpers are `[private]`.
- OS variants (`[linux]`, `[macos]`, …) of one recipe each get the comment.
- Recipes that must run on a remote machine (a VM) say "Run ON THE VM" in the
  comment; the ones run from the laptop don't.
- `just --show <recipe>` prints a recipe, `just --usage <recipe>` its parameters.
- Keep a table of prefix → group → module → area in AGENTS.md; a new area gets
  a new module, prefix, group, import and row.

Typical prefixes (report-bot's modules): `q-` quality, `w-` web frontend,
`g-` desktop GUI run and builds, `db-` migrations, `dk-` docker, `git-` branch
housekeeping, `setup-` machine setup, `vm-` dev VM (from the laptop), `cc-`
Claude Code sessions in tmux, `as-` generated assets, `docs-` docs housekeeping
(backlog list and check).

## Shared verbs

`up` / `down` start / stop; `-fast` is the quick variant of a check, `-check`
the full one.

## Scripts

- More than a few lines of shell, or logic worth testing by hand, goes to
  `scripts/<module>/` (mirrors `just/<module>.just`; also holds that area's
  non-script files such as systemd units). A single-file script stays at
  `scripts/<module>/<name>`; a feature of several files (a script plus its units,
  helpers or data) gets its own folder `scripts/<module>/<feature>/`, file names
  unchanged (installed unit names come from them). A script then finds the repo
  root one level deeper (`parents[3]`) and its siblings relative to itself.
- `#!/usr/bin/env bash`, `set -euo pipefail`, a usage header comment, the
  executable bit, Linux + macOS (bash 3.2; GNU vs BSD `stat`/`sed`/`date`).
- Free-form arguments: `[positional-arguments]` and `"$@"` (`{{ args }}` splits
  quoted values).
- Portable edits in place: `perl -pi -e` (and `perl -0pi` for multi-line),
  not `sed -i`, which differs between GNU and BSD.
- Setup scripts are safe to rerun and never replace a file they didn't create:
  they write a marker line (`# Generated by <repo> scripts/...`) and refuse to
  overwrite a file without it (or skip it with a message).
- Long options (`--requirement`, not `-r`) in committed scripts and docs where
  the tool has them on both platforms.

## Setup recipes

A `setup-` module makes a new machine one command: `setup-all` chains the idempotent steps (the task runner and its
completion, the git hooks, the shortcut command) and ends with `setup-check`, a read-only report that marks each
tool, login and hook as ok, warn (optional) or missing, with the command that fixes it, and exits 1 when a required
one is missing. `setup-upgrade` updates the tools (`uv self update`, `uv tool upgrade --all`, hook revisions) as a
chore. Each step also runs alone, and the first one works before `just` exists (`bash scripts/setup/setup-just.sh`).

Completion goes to the shell the user runs the setup from, not blindly to `$SHELL` (the login shell, often still bash
when people work in zsh or fish): walk up the process tree past the task runner, `sh` and wrapper scripts to the
first known shell, fall back to `$SHELL`, and take a shell name as an argument to override. bash and zsh get a block in their rc file (zsh:
`${ZDOTDIR:-~}/.zshrc`, after `compinit`) that first puts the tool bin dir on `PATH` (terminals that start a non-login
shell never read `~/.profile`, so a bare `eval "$(just --completions <shell>)"` fails with "command not found") and
runs the completion only when `just` is found; fish gets a file in `~/.config/fish/completions/`, rewritten each run.

## Outward-facing recipes

A recipe that publishes, deploys or spends (`rel-publish`, a production
restart) takes an explicit confirmation argument and refuses without it:
`rel-publish confirm="no"` prints what it would run and `Rerun with: just
rel-publish yes`, so an agent cannot trigger it by accident and the rule
"only with the maintainer's OK" is enforced by the recipe, not only by
AGENTS.md. Example: `Alirex/uv_upgrade/justfile`.

## Repo shortcut

A setup recipe (`setup-shortcuts`) installs a `~/.local/bin/<cmd>` wrapper
(default `rb`) that runs `just -f <repo>/justfile "$@"`, so `rb cc-1` works from
any directory, and a `~/<repo>` link to the main checkout. Optional other
command name; it refuses to replace a command it didn't create.

## One-off Python helpers

Scripts that need the project's packages (`uv run python scripts/<module>/x.py`)
end with `raise SystemExit(main(sys.argv[1:]))`, where `main(argv) -> int`
returns the exit code. On bad arguments they print the module docstring (which
holds the usage line) to stderr and return 2. Example:
`report-bot/scripts/db/db_cli.py`.

## Standalone Python scripts (uv)

A script outside any uv project (or one that must not need the project's venv) is a uv script, never a bare
`python3` call: the system Python differs per machine and has no packages.

```python
#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.14"
# dependencies = ["httpx>=0.28"]
# ///
```

- Recipes and hooks call `uv run --script <file>` (the shebang also works for a direct `./file`); uv fetches the
  Python and installs the dependencies into a cached env per script.
- `uv add --script <file> <pkg>` edits the block; `uv lock --script <file>` writes `<file>.lock` when the versions
  must be pinned.
- Inside a uv project, scripts that need the project's packages use `uv run python <file>` instead.

## Small repos without a venv

A notes or docs repo (HQ itself) keeps the same layout with fewer modules: Python helpers are uv scripts
(see below), the checkers (ruff, shellcheck, markdownlint, the justfile formatter) are prek hooks that bring
their own tools, and `q-check` is just `prek run --all-files`. Repo-specific checks are `local` hooks.
Example: HQ's `just/`, `scripts/` and `.pre-commit-config.yaml`.

Mention new or renamed recipes in the README / docs.
